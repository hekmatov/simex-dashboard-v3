## 2. Product vocabulary

| Term | Contractual meaning |
|---|---|
| Add chart | The Build-owned entry action when no chart-creation draft exists. |
| Resume chart draft | The same Build-owned entry action after a suspended chart-creation draft exists. |
| Chart-creation draft | The one dashboard-wide, session-resumable, uncommitted chart definition plus its destination, placement, resource proposals, acknowledgements, and validation state. |
| Pristine draft | A draft with no meaningful user-authored or accepted value, proposal, mapping, configuration, placement, or temporal work. |
| Meaningful draft | A draft containing any user choice, accepted suggestion, entered content, resource proposal, mapping, transform, configuration, placement decision, temporal membership, or completed-stage work whose loss matters. |
| Destination | The named page and section that will own the chart panel and Structure identity if creation commits. |
| Minimum structure proposal | A bounded proposal for the least structure needed to create a valid destination: a new page with its initial section, or an initial section for an existing page. It contains valid identity/context fields, not a nested structure editor. |
| Companion proposal | An uncommitted object needed by the chart: a source, geography resource, minimum structure object, new Time Group, chart-selected Time Group membership, or chart-specific fallback returned only by a linked Time Group workflow. |
| Eligible destination | A destination that can render the chart through the canonical panel surface and expose the same chart identity in Structure. |
| Insertion anchor | A stable neighbouring panel identity plus before/after relation in one named section. It is not an ordinal position. |
| Panel presets | Schema-supported width/span and height choices owned by the destination/layout contract. Free-form geometry is not a preset. |
| Placement projection | A non-mutating calculation over the real section order, neighbour identities, canonical grid rules, insertion slot, selected presets, and projected neighbour reflow. It does not render the chart. |
| Canonical chart preview | The chart-render proof produced by the same renderer, effective data, mappings, transformations, and draft configuration as the final chart. It does not prove page placement. |
| Current preview | A preview result correlated to the latest settled, valid draft revision. |
| Last-good preview | The most recent successful preview retained for diagnostic continuity; it is explicitly marked not current and cannot satisfy create readiness. |
| Schema revision | The registry revision pinned by the draft for its selected chart type and reconciled against the current registry before commit. |
| Compatible | A value can be retained under the prospective type, source, schema, or destination without changing its authored meaning or violating validation. |
| Needs attention | Retained draft work is no longer valid or current and must be repaired, explicitly removed, or re-acknowledged before creation. |
| Linked workflow | A separately owned authoring flow temporarily opened from chart creation and returned to its invoker, such as Create New Time Group. |
| Separate transaction | A saved-object edit, such as shared source-profile repair or saved Time Group repair, committed independently after explicit consequence review; cancelling the chart does not undo it. |
| Create ready | Every required stage is live-complete, every consequential non-default is acknowledged, all dependencies are current, placement and render proofs pass, and the effective chart output contains at least one renderer-ready result. |
| Atomic create | One serialized all-or-nothing write of the chart and only the referenced authorized companion proposals. |
| Ambiguous persistence | A submission outcome in which the system cannot yet distinguish committed from uncommitted strongly enough to retry without risking duplicate chart or companion objects. |
| Scene | The page-scoped saved temporal object defined by the temporal addendum. Chart creation neither redefines Scene semantics nor silently adds a chart to one. |
| Time Group | The dashboard-wide saved temporal object defined by the temporal addendum. One chart may have zero or multiple memberships. |

## 3. Ownership and draft/persistence model

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-OWN-01 | At most one chart-creation draft exists per dashboard in the current application session. Add chart starts it; every later Add chart entry becomes Resume chart draft until that draft is created or explicitly discarded. | Repeated entry never creates parallel or hidden chart drafts. |
| CREATE-OWN-02 | If an ordinary object draft is active when Add chart is invoked, the core Save Changes, Discard Changes, or Stay in Build resolution runs first. The chart draft does not start until the ordinary draft is successfully resolved. | No two ordinary mutation drafts coexist and no prior draft is silently saved or discarded. |
| CREATE-OWN-03 | The chart draft survives Build-surface close, root Escape, mode/page/section navigation, and read-only inspection within the current application session. It does not survive a reload, tab restart, application restart, or new session. | Resume restores the same draft after in-session navigation; a new session starts with no chart draft. |
| CREATE-OWN-04 | Close and root Escape suspend the chart draft. They never save, discard, or clear it. Suspend returns focus to Add chart/Resume chart draft or the entry invoker. | A meaningful draft remains resumable with visible identity and no hidden edit lock. |
| CREATE-OWN-05 | Resume restores the last meaningful focus target when that target still exists and remains actionable. Otherwise it focuses the first current issue; if there is no issue, it focuses the first meaningful control in the current stage. | Focus never falls to BODY or an obsolete control. |
| CREATE-OWN-06 | The draft owns its destination. Active-page, selected-section, mode, or scroll changes outside the draft never retarget it. Resume states when the current external context differs from the retained destination. | Navigation produces a context-difference notice, not a destination mutation. |
| CREATE-OWN-07 | A suspended chart draft may coexist only with navigation and read-only inspection. Starting another ordinary mutation draft requires the user to Create chart or Discard chart draft first. | An attempted page, section, panel, or dashboard edit is blocked by a named chart-draft resolution path. |
| CREATE-OWN-08 | Linked creation of a new Time Group proposal, linked fallback repair for this draft chart, and separately transacted shared source-profile or saved-Time-Group repair are controlled exceptions to CREATE-OWN-07. Chart creation itself exposes only membership selection for zero or multiple existing Time Groups and never authors matching or fallback policy. Opening either linked Time Group path suspends, but does not duplicate or mutate, the chart draft. | Cancelling linked fallback repair returns to the unchanged chart draft and restores focus to its invoker or current temporal issue. Completing it returns exactly one uncommitted chart-specific fallback proposal, restores focus, and revalidates the draft. A separately committed shared-source or saved-group repair returns its durable result and revalidates without becoming a chart companion proposal. |
| CREATE-OWN-09 | Minimum structure, source, geography, new-Time-Group, chart-selected membership, and chart-specific fallback proposals returned by a linked Time Group workflow remain uncommitted until atomic create. They do not appear as saved dashboard objects, exported configuration, View content, Present content, or independent Structure entries before commit. | Cancelling or failing creation leaves no orphan proposed object, no saved chart membership, and no saved fallback. Chart creation contains no direct fallback-authoring control. |
| CREATE-OWN-10 | Atomic create includes only companion proposals referenced by the final chart commit. Unreferenced pristine proposals disappear silently; removing a meaningful now-unused proposal requires a named consequence confirmation. | The review ledger and committed object set match exactly, and meaningful work cannot vanish through backtracking. |
| CREATE-OWN-11 | A separately approved repair to a saved source profile or saved Time Group is durable immediately under its own transaction. Cancelling the chart later does not undo that saved repair. | The chart returns unchanged, revalidates against the new saved dependency, and accurately explains the independent persistence boundary. |
| CREATE-OWN-12 | A meaningful session-only draft requests a reload, tab-close, or application-exit warning where the platform permits. A pristine draft does not warn. | The warning names that the chart draft cannot be resumed after exit; unsupported platform warning capability is not simulated. |

## 4. Entry, destination, and placement semantics

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-DEST-01 | Add chart is available through Build's truthful chart-creation route when no chart draft exists and persistence is not active. Other modes may route to this Build entry. During an active create commit, the route is reason-disabled. | Activating an enabled Add chart always starts or resumes the defined workflow; no enabled entry is inert. |
| CREATE-DEST-02 | On first entry, the active page and selected section supply editable destination defaults. They are never locked merely because they supplied defaults. The named page and section remain visible throughout every stage and Review. | The author can change destination before commit and can always identify where the chart will land. |
| CREATE-DEST-03 | If no valid destination exists, creation may propose the minimum valid page and section. A new page always includes its initial section. The bounded proposal collects required identity and context only and must not expose full nested page/section structure editing. | CREATE-FIX-01 reaches a valid proposed destination without leaving chart creation or creating unrelated structure. |
| CREATE-DEST-04 | A destination is eligible only when the created panel will render on a canonical dashboard panel surface and expose the same chart identity in Structure. Unsupported custom surfaces, including a Home surface that cannot satisfy both, are ineligible. | An ineligible surface remains visible as context where useful, states the reason, and offers a route to choose or create an eligible destination. |
| CREATE-DEST-05 | If a saved destination vanishes or becomes unsupported, the draft becomes Needs attention. It is retained and must be repaired; it is never silently retargeted or appended elsewhere. | Vanished-destination validation produces zero writes and links to Destination. |
| CREATE-DEST-06 | Default placement is append to the named section. The author may instead choose before or after one named neighbouring panel. Placement uses neighbour identity and relation, never a stored ordinal. | The projection and Review both name append or the exact anchor panel and relation. |
| CREATE-DEST-07 | Removal, movement to another section, or invalidation of an insertion anchor blocks creation for repair. There is no silent append fallback. | CREATE-FIX-02's removed and cross-section anchors enter Needs attention with the original choice retained for explanation. |
| CREATE-DEST-08 | If the same anchor identity remains in the same section but section order changes, placement reprojects against the current order. If the projected result changes, Review acknowledgement becomes stale and must be renewed. | Anchor drift is visible in the before/after ordered projection and cannot commit under an old acknowledgement. |
| CREATE-DEST-09 | Destination owns the exposed schema-supported width/span and height presets. Creation shows a safe, visible default and all applicable choices. Zero or one applicable choice remains truthful. Free-form x/y coordinates, arbitrary dimensions, and disguised free-form resizing are unavailable. | The selected presets are named in placement projection and Review and validate against the current destination rules. |
| CREATE-DEST-10 | Chart creation maintains two independent proofs: canonical chart render readiness and placement/context projection. Passing one never implies the other. | CREATE-GATE-H04 can fail either proof independently and Create chart remains unavailable. |
| CREATE-DEST-11 | The placement projection is non-mutating and uses the real target page, section order, neighbour IDs, canonical grid rules, insertion slot, selected width/span and height presets, and projected neighbour reflow. A draft panel is visibly distinct from saved panels. | No saved dashboard geometry changes while projection is inspected; affected neighbours and projected order are accurately listed. |
| CREATE-DEST-12 | The canonical chart preview owns render proof. A miniature, screenshot, placeholder, placement silhouette, or draft panel cannot substitute for it. Conversely, the chart preview cannot claim to prove final placement. | Each proof has a distinct label, state, diagnostics, and Review entry. |
| CREATE-DEST-13 | Placement meaning has an ordered textual equivalent: page, section, insertion relation or append, width/span preset, height preset, and affected neighbours in projected reading order. | A nonvisual user receives every consequential placement value and reflow consequence available visually. |
| CREATE-DEST-14 | Chart-creation controls and projections must preserve the core View/Build parity reference at an equivalent viewport. Authoring chrome cannot change canonical dashboard canvas, grid, panel, or plot geometry. | Core PAR tests remain zero-delta while creation is open, suspended, resumed, reviewed, and handed off. |
| CREATE-DEST-15 | If authoring controls obscure the edited chart content, a current canonical-render substitute satisfying the core VIS/SUB contract must be available. Structural placement work keeps the real destination and affected neighbours inspectable through the placement projection and bounded context navigation. | There is never a state in which both the canonical edited-content proof and its allowed substitute are obscured. |

## 5. Guided workflow stages

### 5.1 Stage model and navigation

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-STAGE-01 | The workflow has exactly six stable behavioral stages in this order: Destination; Chart type; Data source; Map and prepare data; Configure chart; Review and create. Candidate visuals may arrange them differently but must preserve these identities and responsibilities. | Every field, issue, and recovery link has one owning stage; no seventh catch-all stage or merged responsibility is required. |
| CREATE-STAGE-02 | Stage access is dependency-aware and non-linear. The author may activate any stage; missing prerequisites do not masquerade as completion and controls that cannot operate are reason-disabled beside a concise prerequisite explanation. | Direct access to an incomplete downstream stage explains what must happen and links to the prerequisite without clearing work. |
| CREATE-STAGE-03 | Each stage has one derived status from this exact vocabulary: Not started, In progress, Complete, Needs attention, or Waiting on prerequisite. The current-stage marker and issue count are separate from status. | A stage can be current and Needs attention, or non-current and Complete, without contradictory labeling. |
| CREATE-STAGE-04 | Completion is computed live from the current draft and dependencies. Upstream changes invalidate stale downstream completion but retain compatible downstream values. | Changing type, source, destination, time field, or schema revision updates affected statuses without wholesale clearing. |
| CREATE-STAGE-05 | Automatic advancement is permitted only when one unambiguous user selection completes the current stage. Multi-control stages, ambiguous choices, error recovery, and any selection with unresolved consequences use explicit Continue, Back, or direct stage navigation. | A single chart-type or eligible source choice may advance; no user is advanced past a required choice, warning, acknowledgement, or confirmation. |
| CREATE-STAGE-06 | Stage navigation is one composite Tab stop. Arrow keys move focus among stages, Home and End move to bounds, and Enter or Space activates the focused stage and then moves focus to its first meaningful content target. | Keyboard operation completes stage selection without one Tab stop per stage and without leaving focus stranded on the navigation item. |
| CREATE-STAGE-07 | Back and direct navigation preserve compatible work. A destructive prospective change runs compatibility analysis before it applies and follows the named-loss rules in Sections 6, 7, and 9. | Revisiting a stage alone never resets a downstream value. |
| CREATE-STAGE-08 | Schema-owned fields use exactly three disclosure tiers: essential, contextual, and advanced. Essential fields are required or commonly decisive; contextual fields appear when current choices make them relevant; advanced fields require deliberate reveal. | Every applicable capability is reachable, no irrelevant field is shown as operative, and no fourth informal tier hides required work. |
| CREATE-STAGE-09 | Review names every consequential non-default, accepted suggestion, override, proposed companion object, and acknowledgement. Advanced does not mean omitted from Review. | A reviewer can reconstruct the effective authored result without opening every disclosure tier. |
| CREATE-STAGE-10 | Create chart exists only in Review and create. Other stages use Continue, Back, direct navigation, repair, or suspend actions; they cannot commit. | No action outside Review writes a chart or companion proposal. |

### 5.2 Stage responsibilities

| Stage | Binding responsibility | Completion rule |
|---|---|---|
| Destination | Choose an eligible page/section, resolve any minimum structure proposal, choose append or an identity-based insertion anchor, and choose supported panel presets. | The destination and placement projection are valid and current; any meaningful proposal-removal consequence is resolved. |
| Chart type | Search and select a registry chart type with its compatibility explanation and pin its schema revision. | One current, still-discoverable type is selected and no type-change loss decision is pending. |
| Data source | Choose an existing source or create an authorized CSV/manual source proposal; select and validate a geography resource when required; complete source profiling or an approved linked repair. | Required source/geography profiles are current, compatible, and free of blocking coverage or interpretation issues. |
| Map and prepare data | Assign schema-authorized roles; configure transformations, filters, grouping, aggregation, missing-value handling, duplicate-time handling, and explicit interpretations; select zero or multiple existing Time Group memberships; and invoke linked new-group, linked fallback-repair, or separate saved-group-repair routes without exposing temporal policy controls. | All required roles and consequential rules are resolved; effective output is valid and non-empty; and every selected membership/proposal has current effective validation or an explicit repair/removal decision. Upstream time-field, mapping, transform, source, group, or schema changes invalidate only the affected temporal completion. |
| Configure chart | Require or accept a human-readable title and expose every applicable schema-authorized presentation, interaction, and accessibility setting. Temporal policy and placement presets remain in their owning workflows. | Required configuration is valid and the current correlated canonical preview is renderer-ready. |
| Review and create | Present the complete ledger, all problems with owning-stage links, placement and render proof states, current dependency revisions, temporal membership, and every object that will commit. | All entries are current, valid, acknowledged, and create-ready; Create chart may then begin the serialized atomic transaction. |

## 6. Catalogue and data-source behavior

### 6.1 Chart catalogue and schema reconciliation

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-CAT-01 | The chart schema registry is the sole catalogue authority. Acceptance must not depend on today's catalogue count, category count, order, or examples. | CREATE-FIX-03 passes with zero, one, and many registered types and with a changed registry count. |
| CREATE-CAT-02 | Catalogue search matches user-facing chart name, purpose, and description. Results preserve their purpose/category context and an accessible explanation of what each type communicates and requires. | Keyboard and assistive output expose the same identifying and decision-relevant content as visible cards or rows. |
| CREATE-CAT-03 | Compatible, partially compatible, and incompatible types remain discoverable. Partial and incompatible results state the current-data or current-draft reason and a recovery path; they are never hidden to create the appearance of compatibility. | Search results include all matching types and distinguish operability from discoverability without color alone. |
| CREATE-CAT-04 | An incompatible type cannot be selected as if operative and cannot silently clear draft work. A reason-disabled selection names what must change; an intentional type change follows CREATE-CAT-07. | Activating an incompatible result does not mutate the draft and exposes a specific repair path. |
| CREATE-CAT-05 | Zero search results retain the query and filters, announce the zero-result state, explain that search covers name, purpose, and description, and provide Clear search. The system must not silently broaden, substitute, or erase the query. | Clearing is a user action; the empty state remains stable until the query or registry changes. |
| CREATE-CAT-06 | Selecting a chart type pins the draft to the selected schema revision. Immediately before commit, the draft reconciles with the current registry: a compatible revision change is explained and revalidated; an incompatible change requires repair; a removed type blocks while retaining the draft. | Registry drift never silently changes authored meaning or creates under a removed/unknown type. |
| CREATE-CAT-07 | A prospective type change computes which source, geography, mappings, transformations, settings, temporal bindings, and suggestions remain schema-compatible. Before applying any loss, it names every lost category and consequential value. Confirmation is required only when loss exists; cancelling retains the original type and full draft. | A compatible change applies without a gratuitous confirmation and preserves all compatible work; a lossy change cannot apply without named consent. |
| CREATE-CAT-08 | The draft has one active type path. It does not retain internal parallel branches or silently resurrect old incompatible branches when types change. | Backtracking shows the single current draft plus the explicit consequences of the latest accepted change. |

### 6.2 Existing, CSV, manual, and geography sources

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-SOURCE-01 | Existing dashboard sources are searchable and show source identity, visible provenance, current profile summary, and type-specific compatibility reason. Compatible, partially compatible, and incompatible sources remain discoverable. | CREATE-FIX-04's zero, one, many, long-name, and incompatible states preserve identity and reason. |
| CREATE-SOURCE-02 | Zero existing sources does not dead-end creation. Authorized CSV upload, schema-authorized manual data, and required geography routes remain available according to the selected schema. | A valid chart can proceed through each authorized non-existing-source route without fabricating a source. |
| CREATE-SOURCE-03 | CSV upload and schema-authorized manual data create named reusable dashboard-source proposals. They are profiled immediately, display provenance, require a dashboard-unique name, and start from an editable suggested name. They commit atomically with the chart and never become orphans on suspend, discard, failure, or drift. | Before create, the source exists only in the draft ledger; after success, exactly one referenced reusable source exists. |
| CREATE-SOURCE-04 | CSV support accepts at least 2 MiB and 50,000 parsed rows; an implementation may support more. The effective byte, row, format, and any other operative limits are shown before file selection. | Files at the contractual floor can be profiled; a limit violation states the measured value, effective limit, and corrective action. |
| CREATE-SOURCE-05 | CSV limit, parse, and profiling failures retain every safely acquired input, the chart draft, and the last-good profile. If platform file security makes reselection unavoidable, the UI explicitly says which file input cannot be retained and why; it does not imply the rest of the draft was lost. | Retry resumes from the safest retained state and never clears unrelated mappings, destination, or configuration. |
| CREATE-SOURCE-06 | Source profiling has explicit progress/loading, empty, incompatible, invalid, and error states. Progress is bounded and announced; completion is tied to the selected input revision. A failed or incomplete profile cannot satisfy Data source completion. | Out-of-order or stale profiling results never replace a newer selection or enable Continue. |
| CREATE-SOURCE-07 | A successfully loaded source with no detected columns, no rows, or no eligible fields is distinct from a load failure. It retains its identity and profile evidence and explains the relevant repair route. | Empty and invalid profiles do not fabricate columns or masquerade as loading. |
| CREATE-SOURCE-08 | Retry profiling preserves safely acquired input and the last-good profile, marks the old profile stale when the input changed, and revalidates only the affected dependencies. | Unrelated chart work remains intact and stale evidence cannot enable creation. |
| CREATE-SOURCE-09 | A prospective source change runs a compatibility dry run against mappings, transformations, interpretations, geography, and temporal membership. It preserves every valid value, names every loss before applying it, and confirms only when loss exists. Cancelling retains the original source and draft. | CREATE-FIX-10 demonstrates compatible preservation and incompatible named loss without wholesale clearing. |
| CREATE-SOURCE-10 | A required geography resource is a separate reusable dependency, selected from an existing resource or created as a proposal. Its profile identifies geographic identifier interpretation and join coverage against the effective chart data. | Review lists source and geography separately with their provenance and commit status. |
| CREATE-SOURCE-11 | Valid geography coverage may proceed. Partial, low, zero, ambiguous, or unmatched coverage identifies affected identifiers and blocks when the selected schema's minimum safe coverage is not met. Repair never fabricates matches or silently drops unmatched data. | CREATE-FIX-06 routes each deterministic coverage state to proceed or repair using the schema rule. |
| CREATE-SOURCE-12 | Chart-local interpretation ambiguity may be resolved inline using raw examples, detected interpretation, parsing rule, and eligible-role effects. The explicit chart-local choice outranks heuristics and affects only this chart draft. | The draft preview and role eligibility use the accepted override; the shared source profile remains unchanged. |
| CREATE-SOURCE-13 | When ambiguity requires shared-profile repair, chart creation explains what the source editor changes, what the chart draft retains, the shared-source consequences, and the return route. It suspends the chart and opens a separate source-profile transaction that can commit only after explicit consequence review. | Cancelling shared repair returns to the unchanged chart; approving it commits the source repair separately, returns to the invoker, and revalidates the retained chart draft. |
| CREATE-SOURCE-14 | Cancelling chart creation after an approved shared-profile repair does not undo that repair. The discard confirmation names chart-local work only and does not falsely claim to revert the saved source. | Saved profile state remains after chart discard and no compensating rollback occurs. |

## 7. Role mapping, transformations, defaults, and preview

### 7.1 Mapping and preparation

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-MAP-01 | Map and prepare data exposes the full set of roles authorized by the selected schema and applicable to the profiled source: required and optional roles; single and multiple variables; primary and secondary axes; observation/time; cluster; labels; filters; grouping; aggregation; missing values; duplicate-time handling; and chart-family-specific roles. | CREATE-FIX-07 can exercise every named role category without showing an inapplicable role as operative. |
| CREATE-MAP-02 | Role eligibility and cardinality derive from the selected schema, profiled types, accepted interpretations, and chart-type compatibility. Required, optional, single, and multiple cardinalities are programmatically conveyed. | Invalid assignments are prevented or identified with the responsible role and correction; no raw schema is exposed to the author. |
| CREATE-MAP-03 | Only unambiguous, type-compatible defaults may be prefilled. Every prefill is labelled as a suggestion or default, explains its basis, and remains reviewable. Ambiguous analytical choices remain unresolved and block creation. | A default can be distinguished from an explicit user choice; CREATE-FIX-07's ambiguous case is never guessed into Complete. |
| CREATE-MAP-04 | Missing-value and duplicate-time rules are issue-triggered and consequential. A schema may recommend a rule, but the author must explicitly accept or change it before the stage completes. | The selected rule, affected rows/observations, and consequence appear in Review; silence is not acceptance. |
| CREATE-MAP-05 | The workflow exposes every schema-authorized transformation before creation, progressively disclosed by essential, contextual, and advanced tiers. This includes applicable filters, grouping, aggregation, interpretation, missing-value, duplicate, derivation, and chart-family preparation capabilities. | Configure chart is never used to hide an unresolved analytical transformation and no supported current capability disappears. |
| CREATE-MAP-06 | Ambiguous interpretation displays representative raw examples, the detected interpretation, proposed parsing rule, affected eligible roles, and the result of each explicit choice. Explicit choice outranks field-name or browser heuristics. | An ambiguous date cannot silently yield an empty renderer or be changed back by a later heuristic. |
| CREATE-MAP-07 | Filtering, grouping, aggregation, missing-value, duplicate, and interpretation changes recompute the effective output and invalidate only dependent completion, preview, and temporal checks. Compatible mappings remain. | CREATE-FIX-08 demonstrates live invalidation without unrelated draft loss. |
| CREATE-MAP-08 | Zero effective rows, marks, regions, cells, events, or displayed values after preparation is a blocking analytical state, not a ready empty chart. Diagnostics identify whether filtering, missing values, duplicates, mapping, aggregation, or source content caused it and link to the owning control. | The author can repair the exact cause; Create chart remains unavailable. |
| CREATE-MAP-09 | The selected schema supplies a live meaningful-default ledger. For every prefilled or otherwise effective default, the workflow records its value, compatibility/basis, whether explicit acceptance is required, analytical or presentation consequence, dependent completion/proof invalidated by change, and Review visibility. Defaults with no consequential effect may remain implicit; every consequential default must be visible and acknowledged under its owning clause. | CREATE-FIX-07 and CREATE-FIX-08 can enumerate every effective consequential default and distinguish schema default, accepted suggestion, and explicit authored override. |

### 7.2 Configuration and identity

| Clause | Binding requirement | Observable pass condition |
|---|---|---|
| CREATE-CONFIG-01 | Every chart requires a non-empty, human-readable title for Structure identity and assistive technology even when visible title display is disabled. Whitespace-only and machine-only identity values are invalid. | Structure, Review, preview accessibility, and final handoff use the same title identity. |
| CREATE-CONFIG-02 | A suggested title is not silently accepted. The author must explicitly accept it or edit it. The accepted or edited title is recorded as an authored consequential value. | Configure chart cannot become Complete merely because a suggestion is visible. |
| CREATE-CONFIG-03 | Description is optional unless the selected schema explicitly requires it. Hiding a visible description does not erase its saved accessible or contextual value. | Required/optional state follows the schema and Review reports any non-default visibility choice. |
| CREATE-CONFIG-04 | Configure chart exposes all schema-authorized presentation, styling, label, axis, map, timeline, collection, interaction, and accessibility settings that apply to the current type. Essential, contextual, and advanced disclosure may sequence them but cannot omit them. | Existing applicable capabilities remain reachable and inert or irrelevant controls are absent. |
| CREATE-CONFIG-05 | Destination owns panel width/span and height presets. The temporal workflow owns matching, fallback, frames, periods, and playback policy. Configure chart must not duplicate either ownership area under appearance or interactions. | No placement geometry or temporal policy can be edited from Configure chart. |

### 7.3 Canonical preview and readiness
